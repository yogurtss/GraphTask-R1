# GraphTask-R1 专利材料（四部分）

## 建议专利名称

### 推荐名称

**一种领域专用语言驱动的图智能体自进化训练方法**

**English:** *A Domain-Specific-Language-Driven Self-Evolution Training Method for Graph Agents*

该名称突出“领域专用语言（DSL）+ Graph Agent + 自进化训练”，同时保持简洁。说明书中建议将“图智能体”定义为：把自然语言问题编译为受限图程序、调用图执行环境并输出可验证图问答结果的模型，而不是泛指所有图任务智能体。“图任务数据生成与管理”作为方法功能写入摘要和权利要求，不必全部塞入标题。

### 两个备选名称

1. **一种领域专用语言驱动的自进化图智能体方法**
   最短、保护表述较宽，但没有直接点明训练过程。
2. **一种自进化图智能体的图任务生成与管理方法**
   更突出任务数据生成和归档管理，但弱化了 DSL 技术接口。
3. **一种基于领域专用语言的图任务自进化方法**
   更抽象，适合希望弱化具体 Agent 角色时使用。

# Part I. Background of Invention

## Page 1 — Technical Field of Invention

### 页面标题

**Technical Field of Invention｜发明所属技术领域**

### 正式表述

本发明涉及人工智能、图数据处理、智能体训练和领域专用语言（Domain-Specific Language, DSL）技术领域，具体涉及一种利用受限可执行图程序连接语言模型与图执行环境，并通过可认证任务生成、分阶段强化学习和双角色闭环更新实现图智能体自进化训练的方法。

### 页面要点

- **所属领域：** 人工智能、知识图谱、图数据处理、程序合成、强化学习。
- **技术对象：** 能够把自然语言请求转换为可执行图程序的 Graph Agent。
- **核心接口：** 面向图查询与图任务构造的类型化 DSL，即 GraphScript 或功能等效语言。
- **训练目标：** 自动生成、认证和管理图任务数据，持续提升图智能体的程序生成与图问答能力。
- **具体输出：** 可验证图问答结果、执行轨迹、任务证书及受控扩展的任务归档。

### 一句话结论

**本发明属于“DSL 驱动的自进化图智能体”技术，而不是普通的自然语言问答或通用 Agent 调度方法。**

## Page 2 — Description of Prior Art

### 页面标题

**Description of Prior Art｜现有技术说明**

### 现有技术概述

现有大模型图问答系统通常通过两类方式利用图数据：一类是 Prompt-based 方法，将图三元组、子图或文本化图证据拼接到提示中，由语言模型直接生成答案；另一类是 Tool-based Agent 方法，由语言模型在多轮交互中选择图查询、实体检查或文本检索工具，并根据每轮 observation 继续规划。部分系统还采用 Questioner/Proposer 与 Solver 的自博弈框架，用模型自动生成训练问题并更新求解模型。

| 现有路线 | 基本流程 | 典型输出 | 主要能力 |
|---|---|---|---|
| Prompt-based | 问题 + 图谱三元组/检索上下文 → LLM | 自由文本答案 | 快速接入通用大模型，适合简单或短上下文问题 |
| Tool-based Agent | 问题 → 规划 → 工具调用 → observation → 下一步调用 | 多轮调用轨迹 + 最终答案 | 能访问动态、私有或大规模图数据 |
| Query-language generation | 问题 → SPARQL/Cypher/程序生成 → 执行 | 查询程序 + 执行结果 | 可利用数据库执行器完成精确查询 |
| Questioner–Solver self-play | 自动出题 → Solver 求解 → 奖励更新 | 新任务及更新后的模型 | 减少对固定人工标注问题的依赖 |

### 页面讲解文字

这些路线分别解决了自然语言交互、外部知识访问、精确查询和训练数据扩展问题，但通常采用彼此分离的接口、验证标准和训练状态，尚未形成从任务生成到程序执行、任务认证、任务归档和模型更新的统一闭环。

## Page 3 — Problems of Prior Art

### 页面标题

**Problems of Prior Art｜现有技术存在的问题**

| 问题 | Prompt-based 表现 | Tool-based / Self-play 表现 | 技术后果 |
|---|---|---|---|
| 图结构表达不完整 | 图被压平为文本，多跳依赖、方向和 qualifier 容易丢失 | 每次调用只观察局部图信息 | 生成答案与真实图结构不一致 |
| 答案缺少强制执行约束 | 模型可能依赖参数记忆或幻觉关系 | 最终答案可能脱离已检索证据 | 难以证明答案确由指定图产生 |
| 控制流和资源消耗不稳定 | 受上下文长度及提示设计影响 | 多轮调用导致延迟、成本和错误概率累积 | 难以限定图访问范围和执行预算 |
| 中间过程难统一验证 | 自由文本推理不可直接执行 | 不同工具轨迹格式和长度不统一 | 难以复放、比较和定位具体失败步骤 |
| 自进化奖励失真 | 通常只评价最终答案 | 解析失败、执行失败和语义失败常被混为同一低分 | Questioner 可能把接口失败误当作任务难度 |
| 任务库质量难控制 | 缺少程序级任务身份 | 生成任务可能重复、过难、过易或污染训练分布 | 自进化过程不稳定且难以审计 |
| 角色更新相互干扰 | 通常没有独立角色参数 | 混合更新可能改变用于评估的 Solver | 难以保持稳定的难度评价基准 |

### 本发明拟解决的核心技术问题

**在自然语言模型与图执行环境之间建立统一、受限、可执行的 DSL 接口，并基于该接口构建任务生成、执行认证、难度评价、确定性归档和双角色更新的一体化自进化闭环。**

### 页面结论

现有技术的关键缺口不是“能否访问图”，而是缺少一个贯穿**生成—执行—认证—训练—归档**全过程的统一程序合约和可回放状态。

# Part II. Proposed Method and Invention Points

## Page 4 — Summary of Invention

### 页面标题

**Summary of Invention｜发明整体方案**

### 专业摘要式表述

本发明提出一种领域专用语言驱动的图智能体自进化训练方法。该方法获取实例级图快照、关系目录、种子实体、基础任务和执行预算；利用独立 Questioner 同时生成自然语言问题与受限类型化图程序；通过程序解析器和有界图执行器对所述图程序进行结构校验、关系约束校验和资源预算校验，并仅依据认证程序的执行结果生成标准答案；利用冻结 Solver 分别测量程序解析能力、条件执行能力和条件语义求解能力；按照生产、接地和语义前沿阶段计算任务生成奖励，其中语义前沿贡献由 Solver 的接口就绪度门控；将认证任务按照难度和结构/文本新颖性确定性写入任务归档；在同一训练轮次内基于新增任务重建 Solver 数据集，并分别更新 Questioner 与 Solver 的独立适配器。由此输出可验证的图智能体、执行轨迹、任务证书和受控扩展的图任务库。

### 系统组成

| 模块 | 输入 | 核心操作 | 输出 |
|---|---|---|---|
| 实例级环境模块 | 图快照、关系目录、种子、预算、随机种子 | 固定本轮图环境和执行边界 | 可回放环境状态 |
| Questioner 模块 | 种子上下文和允许关系 | 联合生成问题与 DSL 程序 | `{question, program}` |
| 程序执行认证模块 | DSL 程序和图环境 | 解析、类型检查、有界执行、任务认证 | gold、证据、轨迹、证书或拒绝原因 |
| 冻结 Solver 评估模块 | 认证问题和隐藏 gold | 测量解析、执行和语义成功 | 接口就绪度及任务难度信号 |
| 课程奖励模块 | 生成里程碑和 Solver 信号 | 生产→接地→语义前沿分阶段计分 | Questioner 稠密奖励 |
| 归档与课程模块 | 认证任务和评估结果 | 去重、难度/新颖性准入、课程抽样和回放 | Solver 训练数据集 |
| 双角色更新模块 | 角色数据集和独立适配器 | Q→归档→S 同轮依次更新 | 下一轮 Questioner 与 Solver |

### 整体闭环

`实例级图环境 → Questioner 联合生成 → DSL 校验/执行 → 任务认证 → 冻结 Solver 评估 → 确定性归档 → 同轮 Solver 学习 → 下一轮自进化`

### 主要技术效果

- 将自然语言生成转换为可执行、可验证的图操作过程；
- gold、证据和轨迹均可追溯到指定图快照及认证程序；
- 将接口失败与语义难度分离，改善自进化奖励的有效性；
- 控制任务重复、难度漂移及角色参数相互覆盖；
- 形成可序列化、可回放、可审计的训练闭环。

## Page 5 — Invention Point 1: DSL-Driven Bounded Executable Interface

### 发明点

在语言模型与图执行环境之间设置统一、受限、类型化的 DSL，使 Questioner、Solver、训练数据和评测过程共享同一可执行程序合约。

| 项目 | 内容 |
|---|---|
| 解决的问题 | 自由文本推理不可执行；多轮工具轨迹分散且难以统一；图查询资源消耗不可控 |
| 技术手段 | 用 GraphScript 或等效 DSL 显式表示实体解析、关系遍历、集合运算、筛选、比较、验证和结果输出 |
| 合约约束 | 版本、允许算子、SSA 句柄、关系/qualifier 白名单、操作顺序、唯一末端 `emit` |
| 有界执行 | 限制最大操作数、单次遍历上限、边访问量和返回实体量 |
| 可追踪输出 | 保存每步操作、输入/输出句柄、选中/丢弃实体、新增证据、错误码和累计预算 |
| 技术效果 | 统一生成、执行、训练和评测接口，同时实现资源控制、失败定位和过程复放 |
| 保护建议 | 作为独立权利要求的接口基础；不把 GraphScript 名称和具体版本写成必要限定 |

## Page 6 — Invention Point 2: Joint Task Generation and Execution Certification

### 发明点

Questioner 在一次输出中联合产生自然语言问题与对应 DSL 程序，并以认证程序的实际执行结果而非模型生成内容作为 gold answer。

| 项目 | 内容 |
|---|---|
| 解决的问题 | 自动出题可能不可回答、问题与程序不一致或直接泄漏答案 |
| 联合生成 | 输出 `{question, program}`，使自然语言任务与机器可执行逻辑形成显式对应 |
| 认证检查 | 验证种子覆盖、关系/句柄/类型合法性、程序可执行、答案非空、基数要求、问题—程序对齐和无答案泄漏 |
| 认证结果 | 形成包含问题、程序、程序签名、图快照、执行 gold、证据事实和验证摘要的任务证书 |
| 拒绝机制 | 对解析、schema、关系、预算、执行、空结果和泄漏等失败保留结构化原因 |
| 技术效果 | 将模型生成内容转换为可验证训练任务，保证 gold 可追溯到指定图和认证程序 |
| 保护建议 | “联合生成 + 执行认证 + execution-derived gold”是最重要的核心组合 |

## Page 7 — Invention Point 3: Interface-Aware Curriculum Frontier Reward

### 发明点

把 Questioner 学习过程划分为生产、接地和语义前沿三个阶段，并由 Solver 的接口就绪度控制语义难度信号的生效程度。

| 阶段 | 主要评价内容 | 目的 |
|---|---|---|
| Production | 问题/程序存在、JSON、schema、有效算子和有效前缀 | 先学习完整输出合约 |
| Grounding | 种子、关系、句柄、类型、可执行前缀、非空答案、对齐、无泄漏和认证 | 再学习在指定图环境中构造真实任务 |
| Frontier | 在前两阶段基础上评价冻结 Solver 的条件语义成功率 | 最后学习位于 Solver 能力边界的任务 |

### 核心关系

`Interface readiness = parse rate × execution rate given parse`

`Effective frontier weight = configured frontier weight × interface readiness`

语义成功率仅在 Solver 成功解析且成功执行的输出上计算。

### 技术效果与保护

- 避免把 JSON、程序接口或执行失败误判为任务语义难度；
- 在 Solver 接口尚不成熟时继续提供生产和接地阶段的稠密信号；
- 建议保护“接口能力与语义能力分离—条件统计—门控前沿贡献”的组合，不必仅限定乘法形式。

## Page 8 — Invention Point 4: Dual-Role Same-Round Self-Evolution and Task Management

### 发明点

Questioner 和 Solver 使用独立适配器，并按 Questioner 更新、认证任务确定性归档、同轮重建 Solver 数据和 Solver 更新的顺序形成闭环；任务库同时采用难度与新颖性准入以及课程回放控制训练分布。

| 组成机制 | 内容 |
|---|---|
| 参数隔离 | Questioner 和 Solver 分别更新独立适配器；用于评价任务的 Solver 保持冻结 |
| 同轮顺序 | `Questioner update → certify/admit tasks → rebuild Solver data → Solver update` |
| 任务身份 | 依据图快照、程序 canonical signature、问题和轮次形成稳定任务标识 |
| 确定性准入 | 联合 Solver pass-rate 难度窗口、程序结构新颖性和问题文本新颖性 |
| 结构化决策 | 保存 accepted/rejected、难度、新颖性及过难、过易、结构重复和低新颖性原因 |
| 课程管理 | 从较容易的结构分位起步，逐轮扩大范围，并保留简单样本回放 |
| 状态保存 | 记录两个适配器、数据集哈希、归档决策和轮次 manifest，支持恢复与审计 |
| 技术效果 | 防止角色参数相互覆盖，使新任务在产生当轮即可被学习，并控制任务重复、难度漂移和遗忘 |
| 保护建议 | 作为自进化方法的主要闭环创新点；归档和回放作为其内部必要协同机制，不单独强调 |

`DSL 有界可执行接口 → 问题/程序联合生成与执行认证 → 接口感知课程奖励 → 双角色同轮自进化与确定性任务管理`

# Part IV. Detectability

本部分建议直接使用英文。这里的 detectability 指竞争方案中相关技术特征是否能通过产品接口、输出、日志、文档或合法测试被观察，不代表法律上的侵权结论。

## Detectability statement

The invention should be drafted so that at least part of the protected technical chain is externally observable. The inference-side executable-program interface is relatively detectable, while the exact training schedule and reward computation are more likely to remain internal. Accordingly, the broadest claim should include observable input–operation–output features, with internal self-evolution mechanisms preserved as dependent fallback positions.

## Detectability matrix

| Feature | Detectability | Possible evidence source | Drafting implication |
|---|---|---|---|
| A natural-language question is converted into a machine-readable graph program before an answer is returned | High | API responses, SDK objects, debug mode, product documentation, exported traces | Place in the core claim |
| The program uses explicit graph operators, relation identifiers, directions and handles | High | Program output, query logs, error messages, client-side payloads | Define the executable program contract in the core claim |
| Execution is subject to operator, edge-visit or returned-entity budgets | Medium–High | Limit errors, trace metadata, configuration documentation, repeated black-box tests | Include budget enforcement and structured rejection in core/dependent claims |
| The returned answer is accompanied by an execution trace or graph evidence | High | User-visible evidence, audit report, trace endpoint | Claim trace/evidence output where commercially relevant |
| Gold answers are derived exclusively by executing certified programs | Medium | Training-data schema, technical papers, dataset exports, audit records | Protect as a training-method limitation and require certificate records |
| Questioner and Solver use separate adapters | Low–Medium | Model manifests, checkpoint files, technical documentation, leaked or disclosed training artifacts | Use as an important dependent claim, not the only enforcement hook |
| The semantic-frontier reward is gated by interface readiness | Low | Reward logs, training code, experiment reports, discovery or inspection where legally available | Preserve formula and equivalent monotonic combinations as fallback claims |
| Certified tasks are admitted by difficulty and structural/textual novelty | Medium | Archive metadata, rejection codes, task-library behavior, system documents | Claim deterministic admission records and reason codes |
| Newly admitted tasks are consumed by the Solver within the same round | Low–Medium | Round manifests, timestamps, dataset hashes, training logs | Tie the update order to stored round-state artifacts |

## Features that improve practical detectability

- A versioned GraphScript or equivalent program object exposed by the API.
- Structured error codes for schema, relation, execution and budget failures.
- Per-step execution traces containing operators, handles, evidence and cumulative usage.
- Task certificates containing the question, program signature, execution-derived answer and graph snapshot identifier.
- Round manifests containing separate Questioner/Solver adapter identifiers and solver-dataset hashes.
- Archive admission records containing accepted/rejected status, difficulty, novelty and reason codes.

## Recommended claim strategy for detectability

1. Put the observable inference chain—question input, bounded graph-program generation, validation, execution and concrete graph answer—in the principal method claim.
2. Add the certified task record and execution-derived gold as a training-oriented limitation.
3. Protect interface-readiness gating, separate adapters, deterministic admission and same-round dataset rebuilding in layered dependent claims.
4. Claim stored traces, certificates and manifests where they are genuine system outputs; these artifacts improve both replayability and technical detectability.
5. Avoid relying only on an internal reward formula, because a competitor may reproduce the external behavior using an undetectable alternative implementation.

**Short conclusion:** The most detectable protection anchor is the bounded executable graph-program interface and its traceable outputs; the strongest differentiation lies in combining that interface with certified self-evolution mechanisms.
